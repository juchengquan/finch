# Phase 2 — Global merchants (schema baseline change → v0.1)

**Date:** 2026-07-19
**Status:** Design direction approved (grill-me); **needs a detailed plan before building**
(schema + parity coordination + a couple of open scoping questions below).
**Scope:** Make **merchants (counterparties) global** — one catalog shared across all
ledgers — by dropping `counterparties.ledger_id`. This is a **shared-schema change**, so it
is *not* iOS-only. Roadmap: `2026-07-19-ledger-reference-model-roadmap.md`.

**Currencies is re-scoped to ~nothing** (see §Currencies): `exchange_rates` is already global
(PK `(date, currency)`, no `ledger_id`) and the tracked-fetch list is already a global
`app_state` key, so "manage currencies globally" is essentially already true.

## Why global merchants (and why it's the safe one)

A merchant is a real-world entity ("Starbucks" is the same in every book), so a per-ledger
copy of it is duplication, and the **merge** feature we just shipped becomes far more useful
against one shared catalog. It's also the *least entangled* schema change: the cross-ledger
audit only checks accounts + categories (`Audit.swift`), **not** counterparties — so making
merchants global doesn't fight an existing invariant.

## The unlock: pre-launch = no migration

Nothing has shipped, so there is **no data migration**. The change is: edit the baseline DDL,
drop the column + its indexes, and **stamp a fresh schema version (v0.1)**. This is the
cheapest this change will ever be — post-launch it would need a real migration.

## Parity coordination (keep the net, let the web UI lag)

The schema DDL is byte-shared and `Schema.version` is asserted equal to the web's
`SCHEMA_VERSION`; fixtures are generated by running the web `lib/db` as oracle. So Phase 2
moves these **in lockstep**:
1. **Shared schema:** drop `counterparties.ledger_id` (+ `idx_counterparty_ledger`,
   `idx_counterparty_ledger_name` → replace with `(name)` / global name index) in **both**
   `frontend/lib/db/core/schema.ts` and the copied `FinchCore/Storage/Schema.swift`.
2. **Version:** bump the shared version to a fresh baseline (**v0.1** or a new timestamp);
   update the `Schema.version` assertions (SchemaTests / MigrationsTests / PackTests) and the
   baseline migration (a fresh baseline — no incremental migration, since nothing is live).
3. **Both DB layers:** update the web `lib/db/domain/counterparties` + iOS
   `Store/Domain/Counterparties.swift` (drop `ledgerId` from create; queries no longer filter
   by ledger) and the projection/selectors (below).
4. **Re-derive parity fixtures** (`frontend/scripts/export-fixtures.ts`); the web **UI can
   lag** — only the web *DB layer* must move to keep fixtures generatable.

## Affected surface (iOS)

- **`createCounterparty`**: drop the `ledgerId` arg; merchants are global.
- **`Projection`/`Projections+State.counterparties`**: fetch **all** counterparties (no
  `WHERE ledger_id = ?`); `store.merchants` becomes the global catalog (no longer re-projected
  on ledger switch → the Merchants page stops changing when you switch ledgers, the goal).
- **Selectors** `counterpartyTxCounts` / `merchantTransactions`: resolve merchant by
  id/name **globally**, but see the open question on which *transactions* to count.
- **Merge** (`mergeCounterparty`/`mergeCounterparties`): drop the same-ledger guard (all
  merchants share a scope now); reassignment of `entries.counterparty_id` is unchanged.
- **UI** (`MerchantsView`, `CounterpartyDetailView`): unchanged in shape; just fed the global
  list. This is also why the Settings "Ledger" group would no longer be the right home for
  Merchants — it'd move (to General, or its own row) — a small follow-up.

## Open questions to resolve in the plan

1. **Count/detail scope.** With a global catalog, does a merchant's **count pill** and its
   **detail transactions** span *all ledgers* or just the *active* ledger?
   *Recommendation:* **active-ledger** counts/detail by default (money figures already convert
   per active-ledger base; cross-ledger sums would mix currencies), with the global catalog
   simply meaning the *row list* no longer changes on ledger switch. Revisit if a global
   "total across books" view is wanted.
2. **Merchant name uniqueness.** Global + the existing case-insensitive `name` index: do we
   enforce one "Starbucks" globally (unique), or allow dupes and lean on merge?
   *Recommendation:* keep it non-unique (as today) + rely on merge; a hard global-unique
   constraint is a behavior change that can strand imports.
3. **Verified + counterparty-name override** semantics are unchanged (both already
   id-based), but confirm the projection's name-override still resolves globally.

## Currencies (re-scoped)

`exchange_rates` is already global and `fxTrackedCurrencies` is already a global key, so **no
schema change is needed for currencies.** The only thing per-ledger is each ledger's **base
currency** (inherent, chosen at creation). The one *optional* addition — a **per-ledger
"activated currencies" set** (so ledger A can surface EUR/GBP while ledger B surfaces JPY) —
is an `app_state`-level, per-ledger key (no `exchange_rates` change) and is **deferred**: the
current global tracked-list + auto-fetch already works, and per-ledger activation is a nicety,
not the reported pain. Pull it into its own tiny spec only if wanted.

## Migration / risk
- **No data migration** (pre-launch). The risk is breadth (two platforms, fixtures, version
  bump), not depth. Do it while pre-launch keeps it cheap.
- **Parity window:** between changing the schema and re-deriving fixtures, parity tests for
  `counterparties` will fail — land the schema + fixture regen atomically.
- **Audit:** minimal — counterparties were never cross-ledger-audited.

## Testing
- Web + iOS: schema-version assertions updated to v0.1; `swift test` green incl. re-derived
  parity fixtures; `mergeCounterparty` cross-ledger guard removed + tests updated; new tests
  that `store.merchants` is global and stable across ledger switch. iOS + macOS build.
